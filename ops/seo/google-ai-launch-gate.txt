Below is the launch-gate checklist I would standardize across your studio. It deliberately separates **Google requirements, Google recommendations, AI/agent readiness, and unsupported SEO folklore**. Google explicitly says generative-AI Search still rests on conventional Search fundamentals ([Google for Developers][1]), and `llms.txt` is not used by Google Search. ([Google for Developers][2])

# A2A GOOGLE + AI-ERA WEBSITE PRE-LAUNCH GATE

## PURPOSE

Run this audit **after the site is functionally complete but before production launch**.

The agent must:

1. Inspect the actual deployed candidate.
2. Test rather than assume.
3. Produce evidence for every PASS.
4. Score the site from **0.0–10.0**.
5. Identify exactly what must be fixed.
6. Re-run failed checks after fixes.
7. Refuse to declare the site launch-ready unless it reaches **8.5/10 or higher with zero P0 blockers**.
8. Never claim Google indexing, ranking, AI Overview inclusion, or traffic is guaranteed.

Google explicitly states that satisfying its requirements does **not** guarantee crawling, indexing, serving, or ranking. ([Google for Developers][3])

## AUDIT RULES

Use these classifications:

**MUST** = failure can prevent normal Search eligibility, violate policy, or fundamentally break discovery.

**SHOULD** = Google-recommended practice that improves discovery, understanding, Search appearance, quality, or user experience.

**CONDITIONAL** = required only when the site type or feature applies.

**AGENT** = improves browser-agent/AI-agent usability but must not be misrepresented as a confirmed Google ranking factor.

**DO NOT SCORE** = myths, unsupported tricks, or optional technologies Google says are unnecessary.

### Evidence rule

Never mark PASS from code assumptions alone.

Acceptable evidence includes:

* HTTP response inspection
* rendered browser output
* rendered DOM
* page source
* robots.txt inspection
* sitemap inspection
* structured-data validation
* crawl results
* Lighthouse/PageSpeed evidence
* Search Console evidence when access exists
* URL Inspection evidence when access exists
* screenshots for visual/mobile findings

When evidence cannot be obtained:

**STATUS = UNVERIFIED**

An UNVERIFIED item cannot receive full credit.

# 1. SEARCH ELIGIBILITY — 15 POINTS

These are the first checks.

Google's minimum technical requirements are:

1. Googlebot is not blocked.
2. The page returns a working HTTP `200`.
3. The page contains indexable content.

Meeting them creates eligibility, not guaranteed indexing. ([Google for Developers][1])

### [MUST] 1.1 Production accessibility

Check:

* homepage resolves
* important landing pages resolve
* no authentication wall on public pages
* no DNS failure
* no broken SSL/TLS
* no production maintenance screen
* intended indexable pages return `200`

FAIL examples:

* 4xx/5xx on critical pages
* redirect loops
* staging password protection
* blank client-side shell that fails to render

### [MUST] 1.2 Googlebot access

Inspect:

`/robots.txt`

Verify important public pages and necessary resources are not accidentally blocked.

Remember:

`robots.txt` primarily controls **crawling**, not reliable removal from Google's index.

Use `noindex` when an accessible page should not appear in Search. ([Google for Developers][4])

### [MUST] 1.3 Index directives

Inspect critical templates for:

* `noindex`
* `nofollow`
* `none`
* conflicting `X-Robots-Tag`
* accidental staging directives

Also inspect snippet controls.

Important:

`nosnippet` also prevents content from being used as a direct input for Google AI Overviews and AI Mode. ([Google for Developers][4])

### [MUST] 1.4 Indexable primary content

Confirm that meaningful page content exists in Google's rendered version.

Do not pass pages whose useful content exists only after:

* a click
* a swipe
* typing
* login
* unsupported client interaction

Google explicitly warns that primary content requiring user interaction to load may not be seen during crawling/rendering. ([Google for Developers][5])

# 2. URL ARCHITECTURE, CANONICALIZATION + DISCOVERY — 10 POINTS

### [SHOULD] 2.1 Every important resource has a stable URL

Verify meaningful pages have distinct, crawlable URLs:

* services
* products
* projects
* articles
* events
* locations
* major categories

Avoid hiding important content entirely behind application state with no addressable URL.

### [SHOULD] 2.2 Canonical correctness

For representative pages inspect:

* canonical exists where appropriate
* canonical points to intended version
* HTTPS version preferred
* query/tracking variants do not create accidental duplicates
* sitemap and canonical agree
* staging/previews are not canonical targets

Google performs canonicalization itself, but site owners can provide canonical signals. Duplicate content is normal and is not automatically a spam violation. ([Google for Developers][6])

### [SHOULD] 2.3 Redirect integrity

Check:

* HTTP → HTTPS
* old URLs → correct replacement
* www/non-www consistency where applicable
* no redirect chains where avoidable
* no loops
* no deceptive redirects

### [SHOULD] 2.4 Crawlable internal links

Important navigation links should generally be real:

`<a href="...">`

Every important page should be reachable from at least one other crawlable page.

Google says links help it both **discover pages** and understand relevance. ([Google for Developers][7]) Avoid orphan pages.

* onclick-only navigation
* empty anchors
* broken internal links
* links to redirected/dead URLs

### [SHOULD] 2.5 Descriptive anchor text

Prefer meaningful text describing the destination.

Avoid repeatedly using:

* Click here
* Learn more
* More
* Website

when a more descriptive label makes sense.

Do not keyword-stuff anchors. ([Google for Developers][7])

# 3. SITEMAP + DISCOVERY SIGNALS — 5 POINTS

### [SHOULD] 3.1 XML sitemap

Verify sitemap exists when useful.

Check:

* returns `200`
* valid format
* canonical production URLs only
* no staging URLs
* no `noindex` URLs
* no 404/5xx URLs
* absolute URLs
* accurate `lastmod` when used

Google says sitemaps help communicate new or updated URLs, but they are suggestions rather than guarantees that every URL will be crawled. ([Google for Developers][8])

### [SHOULD] 3.2 robots.txt sitemap reference

Where appropriate verify:

`Sitemap: https://example.com/sitemap.xml`

### [SHOULD] 3.3 Search Console submission

When access exists:

* verify property ownership
* submit sitemap
* confirm sitemap processing status

Google notes pages can be discovered without sitemap submission, though submitting one can help discovery and monitoring. ([Google for Developers][9])

# 4. JAVASCRIPT + RENDERING — 8 POINTS

### [MUST] 4.1 Rendered content exists

Test representative pages with JavaScript enabled and rendered DOM inspection.

Verify that Google can ultimately see:

* main content
* headings
* links
* titles
* canonical
* structured data where used
* important images
* navigation

Google crawls, renders JavaScript with a modern Chrome environment, then processes content, but JavaScript sites introduce additional complexity. ([Google for Developers][10])

### [MUST] 4.2 Critical content is resilient

Prefer architectures where essential discoverable content is not unnecessarily dependent on fragile client-side execution.

Flag:

* blank initial shells
* API failures producing empty pages
* hydration failures
* client-side metadata that never appears
* JS-generated links without valid anchors

### [SHOULD] 4.3 Render verification

Where Search Console access exists:

Use URL Inspection on representative templates.

Test at minimum:

* homepage
* service/product page
* article/content page
* location page when relevant
* deepest important URL

# 5. PAGE TITLES, HEADINGS + SEARCH SNIPPETS — 10 POINTS

### [SHOULD] 5.1 Unique `<title>`

Every important indexable page should have a descriptive, concise title representing that specific page.

Avoid:

* missing titles
* duplicate sitewide titles
* keyword stuffing
* generic titles such as “Home”
* stale dates
* excessive boilerplate

Google automatically creates title links using multiple signals, including `<title>`, visible headings, page text, anchors, and other prominent content. ([Google for Developers][11])

### [SHOULD] 5.2 Clear primary page heading

Verify:

* obvious main page topic
* visually prominent heading
* logical heading hierarchy
* headings describe actual content

Do not treat “one and only one H1” as a magical ranking rule.

Score clarity, not folklore.

### [SHOULD] 5.3 Meta description

Verify important pages have useful, accurate descriptions when appropriate.

Do not assume Google will always display them.

Google primarily generates snippets automatically from page content and may use the meta description when it better describes the page. ([Google for Developers][12])

### [DO NOT SCORE] Meta keywords

Do not award points for:

`<meta name="keywords">`

Do not recommend adding it as an SEO tactic.

# 6. CONTENT QUALITY + AI-GENERATED CONTENT — 15 POINTS

This is a major scoring category.

Google says its ranking systems are designed to prioritize helpful, reliable, people-first information rather than content created primarily to manipulate rankings. ([Google for Developers][13])

### [SHOULD] 6.1 Clear visitor purpose

For every major page ask:

* Who is this for?
* What problem does it solve?
* What action should the visitor take?
* Does the page satisfy that purpose?

### [SHOULD] 6.2 Unique value

Check whether the site contributes something beyond generic AI summaries or rewritten competitor content.

Look for:

* firsthand experience
* original photos
* case studies
* actual project evidence
* original research/data
* expert explanations
* genuine comparisons
* specific local knowledge
* unique tools/features
* documented outcomes

Google's current generative-AI guidance specifically emphasizes **unique, valuable, non-commodity content** and warns against simply recycling what already exists online. ([Google for Developers][14])

### [MUST/POLICY] 6.3 No scaled low-value AI content

Search for:

* mass-generated location pages with trivial word swaps
* thousands of near-identical pages
* AI-written pages with no added value
* scraped/recombined content
* auto-generated keyword pages
* fake expertise
* content created mainly to capture every query variation

Google defines scaled content abuse based on producing large amounts of low-value content primarily to manipulate rankings, regardless of whether AI, automation, humans, or combinations produced it. ([Google for Developers][15])

### [MUST] 6.4 AI factual QA

For AI-assisted content:

Verify:

* claims are accurate
* names are correct
* dates are correct
* addresses are correct
* prices/hours are current where relevant
* citations actually support claims
* invented testimonials do not exist
* fake statistics are absent

Google recommends accuracy, quality, and relevance for automatically generated content and metadata. ([Google for Developers][16])

### [SHOULD] 6.5 Natural language

Write for the user.

Do not:

* stuff keywords
* mechanically repeat search phrases
* produce dozens of pages for lexical variations
* rewrite content solely “for AI”

Google says its AI/Search systems understand synonyms and meaning and specifically rejects the need to capture every long-tail variation. ([Google for Developers][2])

# 7. STRUCTURED DATA + MACHINE UNDERSTANDING — 8 POINTS

### [CONDITIONAL/SHOULD] 7.1 Correct schema

Use only schema appropriate to actual visible content.

Examples when applicable:

* Organization
* LocalBusiness
* Product
* Event
* Article
* Breadcrumb
* JobPosting
* Video
* ProfilePage

Google says structured data provides explicit clues about page meaning and can make pages eligible for richer Search experiences. ([Google for Developers][17])

### [MUST] 7.2 Structured data truthfulness

Verify structured data:

* matches visible page content
* contains no fake ratings/reviews
* contains current facts
* uses supported types correctly
* contains required fields
* is not misleading

### [SHOULD] 7.3 Validate markup

Run relevant pages through Google's Rich Results Test or equivalent Google validation.

Fix errors.

Review warnings pragmatically.

Google recommends validation and explicitly states valid structured data does **not guarantee** a rich result. ([Google for Developers][18]) MYTH RULE

Do **not** call schema a guaranteed ranking boost.

Do **not** create fake or excessive schema simply to “feed AI.”

Google states there is no special schema required for generative-AI Search. ([Google for Developers][2])

# 8. MOBILE + PAGE EXPERIENCE + CORE WEB VITALS — 12 POINTS

Google uses the mobile version of site content for indexing and ranking. ([Google for Developers][5])

### [SHOULD] 8.1 Mobile equivalence

Verify mobile contains the same essential:

* primary content
* important links
* headings
* metadata
* structured data
* important images/video

Do not hide critical SEO-relevant content only on desktop.

### [SHOULD] 8.2 Responsive usability

Test common phone widths.

Check:

* text readability
* tap targets
* menus
* forms
* horizontal overflow
* sticky overlays
* modals
* CTAs
* image cropping
* navigation

### [SHOULD] 8.3 Core Web Vitals

Target Google's “good” thresholds:

* **LCP ≤ 2.5 seconds**
* **INP < 200 ms**
* **CLS < 0.1**

Use field data when available; supplement with lab diagnostics.

Google recommends good Core Web Vitals but explicitly says perfect scores do not guarantee top rankings. ([Google for Developers][19])

### [SHOULD] 8.4 Overall page experience

Check:

* HTTPS
* mobile display quality
* intrusive interstitials
* distracting ad overload
* ability to distinguish main content
* major usability barriers

Google says there is no single “page experience” signal; multiple aspects contribute to overall experience. ([Google for Developers][20])

# 9. IMAGES, VIDEO + MULTIMODAL DISCOVERY — 5 POINTS

### [SHOULD] 9.1 Images are technically discoverable

Check important images for:

* valid supported image usage
* descriptive surrounding context
* meaningful alt text where appropriate
* reasonable filenames where useful
* accessible URLs
* not accidentally blocked from crawling

### [SHOULD] 9.2 Alt text quality

Alt text must primarily serve accessibility and accurately describe meaningful images.

Do not stuff keywords.

For linked images, Google can use image alt text as anchor context. ([Google for Developers][7])

### [SHOULD] 9.3 Original multimedia

Reward relevant:

* original photography
* demonstrations
* diagrams
* project evidence
* videos

especially where they add information not present in generic text.

Google says images and video can create additional opportunities for visibility in generative AI Search experiences. ([Google for Developers][14])

# 10. AI SEARCH + GENERATIVE SEARCH READINESS — 5 POINTS

### [MUST FOUNDATION] 10.1 Normal Search eligibility first

Do not create a separate fake “GEO score” disconnected from Search fundamentals.

To be eligible as supporting content in Google's generative AI Search experiences, pages must first satisfy normal Search/indexing eligibility requirements.

Google says generative AI Search features are rooted in core Search ranking and quality systems. ([Google for Developers][2])

### [SHOULD] 10.2 Citation-worthy page quality

Ask:

Could a search system confidently use this page as a source?

Evaluate:

* clear answer/topic
* factual specificity
* visible supporting evidence
* original value
* current information
* clear entity/business identity
* relevant supporting media
* trustworthy references where appropriate

Do not convert this into arbitrary “AI keyword density.”

### [DO NOT SCORE] 10.3 llms.txt

Do **not** penalize a site for lacking:

* `llms.txt`
* `llms-full.txt`
* special AI Markdown files

Google explicitly states Google Search does not use these files and that adding them neither helps nor hurts Google Search visibility or ranking.

They may optionally be maintained for **other systems that explicitly support them**, but not as a Google optimization. ([Google for Developers][2])

### [DO NOT SCORE] 10.4 Fake GEO/AEO hacks

Do not recommend:

* artificial “AI mentions”
* keyword stuffing for LLMs
* tiny-content chunking solely for AI
* hundreds of fan-out-query pages
* unsupported “AI schema”
* third-party proprietary authority scores presented as Google metrics

Google's current guidance explicitly warns against several of these supposed generative-AI optimization hacks. ([Google for Developers][2])

# 11. BROWSER AGENT READINESS — 5 POINTS

This category concerns agents acting as web users.

Do **not** misrepresent these items as confirmed Google ranking factors.

Google's web.dev guidance explains that modern browser agents may inspect screenshots, DOM structure, and the accessibility tree. ([web.dev][21])

### [AGENT] 11.1 Semantic controls

Prefer real semantic elements:

* `<a>` for navigation
* `<button>` for actions
* `<input>`
* `<select>`
* properly connected `<label>`

Avoid fake clickable `<div>` elements where standard controls should be used.

### [AGENT] 11.2 Accessibility tree

Audit whether:

* controls have understandable accessible names
* fields have associated labels
* navigation hierarchy makes sense
* hidden overlays do not block actions
* dialog state is understandable
* interactive elements are detectable

### [AGENT] 11.3 Stable task paths

Test common actions as an agent would:

* find contact information
* submit inquiry
* book
* donate
* buy
* register
* find price
* compare products/services

Flag visually obvious actions that are machine-ambiguous.

### [OPTIONAL/EXPERIMENTAL]

Emerging agent protocols may be evaluated separately.

Do not make experimental protocols such as emerging WebMCP/UCP-style approaches a universal launch requirement unless the site's use case justifies them.

# 12. TRUST, SECURITY + SPAM COMPLIANCE — 7 POINTS

### [MUST] 12.1 HTTPS

Production pages should be securely served.

### [MUST/POLICY] 12.2 Spam-policy review

Search for:

* hidden text created to manipulate ranking
* hidden spam links
* cloaking
* deceptive redirects
* doorway-style pages
* scaled content abuse
* link manipulation
* scraped low-value content
* site reputation abuse
* misleading functionality

Google's spam policies can result in reduced ranking or removal from Search. ([Google for Developers][15])

### [MUST/POLICY] 12.3 Paid/user-generated links

Where applicable use appropriate relationship attributes such as:

* `sponsored`
* `ugc`
* `nofollow` where justified

Do not automatically nofollow every legitimate external citation.

Google provides specific guidance for qualifying commercial and user-generated links. ([Google for Developers][22])

### [SHOULD] 12.4 External factual citations

Where factual claims require evidence, cite trustworthy primary sources.

Do not invent sources.

Google's link guidance explicitly notes that external links can help establish trustworthiness when used naturally to cite sources. ([Google for Developers][7])

# 14. SEARCH CONSOLE + MEASUREMENT — 5 POINTS

### [SHOULD] 14.1 Search Console property

Verify ownership when credentials/access are available.

Never fabricate Search Console evidence.

### [SHOULD] 14.2 URL Inspection

Inspect representative important pages for:

* indexing status
* crawlability
* Google-selected canonical
* rendered resources
* live-test issues

Google describes URL Inspection as the preferred page-level debugging source for crawl/index information. ([Google for Developers][9])

### [SHOULD] 14.3 Indexing reports

Review:

* indexed URLs
* excluded URLs
* errors
* unexpected canonicalization
* manual actions
* security issues

### [SHOULD] 14.4 Search performance

Establish baseline measurement for:

* impressions
* clicks
* queries
* landing pages
* countries/devices where relevant

### [OPTIONAL WHEN AVAILABLE] 14.5 Generative AI Search visibility

Review Google's Generative AI performance report when the property has access.

Google announced dedicated reporting for visibility in AI Overviews, AI Mode, and generative AI features in Discover, initially rolling it out to a subset of sites. ([Google for Developers][23])

## SCORING SYSTEM

Calculate only applicable points.

**Normalized score:**

`earned applicable points ÷ possible applicable points × 10`

Round to one decimal.

## Rating

### 9.5–10.0 — EXCEPTIONAL

Technically sound, highly discoverable, strong content, agent-ready, and fully evidenced.

### 9.0–9.4 — LAUNCH READY

Strong production launch candidate. Only minor improvements remain.

### 8.5–8.9 — CONDITIONAL PASS

May launch only if there are **zero P0 blockers** and remaining issues have explicit owners.

### 7.0–8.4 — HOLD

Not ready under studio standards. Resolve major weaknesses first.

### 5.0–6.9 — FAIL

Material discovery, content, technical, UX, or measurement problems.

### 0.0–4.9 — BLOCKED

Fundamental production/Search eligibility or integrity failures.

# HARD SCORE CAPS

Apply these **after** calculating the raw score.

## Maximum 3.0/10

If any of these affect major public pages:

* site inaccessible
* critical pages return persistent 5xx
* production requires authentication
* entire intended public site blocked from Googlebot
* sitewide accidental `noindex`
* broken DNS/SSL preventing normal access

## Maximum 4.0/10

If:

* primary page content fails to render for crawlers
* deceptive spam practices are detected
* serious scaled-content abuse exists
* canonical configuration points major production pages to the wrong domain/environment

## Maximum 6.0/10

If:

* mobile version omits major primary content
* important pages are mostly orphaned
* large portions of the sitemap are broken/noncanonical
* major templates lack meaningful unique content
* critical conversion journeys are broken

A visually beautiful website does not override a hard technical blocker.

# PRIORITY SYSTEM

For every failure create a repair item.

## P0 — BLOCK LAUNCH

Examples:

* indexing blocked
* site unavailable
* wrong canonical domain
* critical render failure
* broken checkout/donation/contact flow
* serious spam-policy violation
* security failure

## P1 — FIX BEFORE LAUNCH

Examples:

* important orphan pages
* missing unique titles across major templates
* mobile content mismatch
* invalid critical structured data
* major CWV/performance failures
* weak or commodity primary content
* broken internal navigation

## P2 — FIX SOON AFTER LAUNCH

Examples:

* metadata improvements
* alt-text cleanup
* secondary schema enhancements
* internal linking refinements
* minor performance improvements

## P3 — EXPERIMENT / OPTIONAL

Examples:

* `llms.txt` for a non-Google system that explicitly supports it
* emerging agent protocols
* experimental rich interfaces
* nonessential schema enhancements

P3 work must never delay revenue or production proof unless required by the business model.

# FINAL ANTI-NONSENSE RULES

The agent must never award SEO points merely because:

* `llms.txt` exists
* meta keywords exist
* a page reaches arbitrary keyword density
* every page has an exact-match keyword
* content reaches an arbitrary word count
* schema exists regardless of correctness
* a third-party “Domain Authority” score is high
* an AI-generated page merely contains lots of text
* Lighthouse is 100
* dozens of pages were published
* backlinks were purchased
* the site was submitted to a “search submission service”

Google's own documentation emphasizes Search eligibility, crawlability, helpful and original content, natural linking, valid technical implementation, good overall page experience, and policy compliance rather than magical optimization tricks. ([Google for Developers][3])

## DECISION

**Adopt this as the mandatory final optimization gate for every public website.**

## CHANGES

The important change from a normal SEO checklist is that this evaluates four separate things instead of collapsing them into one vague “SEO score”:

**Search eligibility → Search understanding/quality → AI Search readiness → browser-agent usability.**

It also explicitly gives **zero credit to `llms.txt` for Google**, because Google's July 2026 guidance says Google Search ignores it. ([Google for Developers][2])

This framework is grounded primarily in current Google Search Central documentation, including the July 10, 2026 generative-AI optimization guidance, Search Essentials, technical requirements, Search Console, structured-data policies, mobile-first indexing, Core Web Vitals, and Google's April 2026 agent-friendly web guidance. ([Google for Developers][14])

**Workflow specification: ready. Actual site score: not yet measured**, because this request did not identify a specific production URL to audit.

## COMMERCIAL IMPACT

This can become one standardized QA skill across your studio instead of buying separate “SEO,” “GEO,” and “AI optimization” audits. The strongest commercial packaging is to make this one of the verification engines inside your **Vibe Audit → Rescue Sprint → Sovereign Launch** process.

## RISKS

Google explicitly does not guarantee crawling, indexing, ranking, or AI-feature inclusion. A 10/10 therefore means **verified optimization against documented requirements and best practices**, not guaranteed rankings. ([Google for Developers][10])

The audit itself is read-only. Any automated remediation should require a git commit/PR, deployment preview, before/after evidence, and reversible rollback.

## NEXT

Run this exact gate against the next production site before changing anything, establish its **real 0–10 baseline**, then fix P0 → P1 issues only.
